# Design

## Context

**Design reference:** the approved mockup is `docs/design/recipe-editor.html` (static, open it in a browser; see `docs/design/README.md`). It shows the layout, every chip state and the keyboard toolbars; the app's own tokens in `packages/web/app/app.css` win where the two differ.

`recipe-storage` already holds an ingredient as `quantity_text` (as typed), optional `amount` and `unit`, `name` and a `position`; `getRecipe` returns only `quantity_text` and `name`; `createRecipe` accepts `{name, quantityText, amount, unit}[]`; there is no `updateRecipe` path for ingredients. The editor shell and its `Draft` come from `edit-recipe-basics`: a section receives its slice and `onChange`, and lists post as a hidden JSON input. The approved mockup fixes the row: grip, a soft toolbar group (stacked ↑ ↓ pair with the delete button beside it), the field, and a small "Gebruikt in stap N" line below the field.

## Goals / Non-Goals

**Goals:**
- Typing an ingredient is as fast as writing it; the parsed quantity is visible while typing.
- One parser, used by the browser (live highlight), the server (what is stored) and `edit-recipe-chips`.

**Non-Goals:**
- Pasting or importing a list, English units (the import feature, later), unit conversion or scaling (cards #17, #18), an ingredient picker or autocomplete.

## Decisions

- **Draft shape.** `Draft.ingredients: { id: string; text: string }[]`, where `text` is the raw line. `id` is a client-only stable key (a counter in the reducer; never posted), needed for focus, drag and the later chip links. The editor guarantees one empty trailing row (a normalising function on every change), so "typing adds a row" is not a special case in the component.
- **Parser** (`lib/ingredients.ts`, pure, tested): `parseIngredient(text) → { quantityText, amount?, unit?, name }` with `quantityText` the leading quantity exactly as typed (including its internal space, e.g. `250 g`). Grammar, in order: optional leading spaces; a *number* = digits with optional `,` or `.` decimals, or a unicode fraction (`½ ⅓ ⅔ ¼ ¾ ⅛`), or `a/b`, or a whole number directly followed by a fraction (`1 ½`); optionally a range (`2-3`, giving `amount` undefined, as it cannot be scaled); then, after optional whitespace, a *unit* only when the next word (case-insensitive, optional trailing dot) is in a fixed Dutch list (g, gr, gram, kg, mg, l, liter, dl, cl, ml, el, tl, kl, snuf, snufje, scheut, scheutje, klont, klontje, blik, blikje, pot, potje, zak, zakje, bos, bosje, teen, tenen, takje, takjes, plak, plakken, plakje, stuk, stuks, stukje, bakje, pak, pakje, handvol, mespunt, mespuntje, eetlepel(s), theelepel(s)). Everything after is the name, trimmed. No leading number → `quantityText = ''` and the whole text is the name. `amount` is the numeric value (fractions evaluated; `1 ½` is 1.5), `unit` the unit word lowercased without its dot. An unlisted word after a number stays in the name (`2 grote uien`), which keeps the grammar predictable: the user never has to guess what counts as a unit. Chosen over a general NLP/unit library: a short fixed list is testable and the failure mode (word lands in the name) is harmless.
- **Round trip.** A stored ingredient is shown as `quantity_text + ' ' + name` (just the name when the quantity is empty). If a stored pair would re-parse differently (an exotic stored quantity) the line still reads the same; only the stored split could change on the next save, which is cosmetic and accepted.
- **Colouring text inside an input.** Browsers cannot colour part of an `<input>`'s text, so each row is a grid of two stacked layers: a mirror `<div>` (aria-hidden, `white-space: pre`, `overflow: hidden`) that shows the text with the quantity in a `<b>` coloured `blu`, and the real `<input>` over it with `color: transparent` and a visible `caret-color`. Both share font, size, weight and padding exactly (no weight difference between the two layers, otherwise glyph widths drift), so every character index is in the same place in both. Rows stay one line (the mirror never wraps); the input's `scrollLeft` is copied to the mirror on `input` and `scroll` so long lines stay aligned. Selection highlight and the caret come from the real input, so editing behaves natively. Chosen over `contenteditable`: IME, undo and mobile keyboards stay native.
- **Keys.** `Enter` moves to the next row's input (and is prevented from submitting the form); `ArrowDown`/`ArrowUp` move to the next or previous row's input (single-line inputs have no other use for them, as in a spreadsheet); `Backspace` in an empty non-last row removes it and focuses the end of the previous one. **Tab is never remapped**: there is no reliable, appropriate way to detect assistive technology (and detecting it would expose a disability), so the page is one interface for everyone and follows WCAG 2.1.1, 2.1.2 and 2.4.3 and the ARIA Authoring Practices, where Tab moves between widgets and arrow keys move inside them. The delete button removes the row and moves focus to the next row's field (or the empty row).
- **Keyboard cost per row.** The row's up, down and delete buttons form one `role="toolbar"` (`aria-label` "Acties voor ingrediënt N") with a roving tabindex: one Tab stop, `ArrowLeft`/`ArrowRight` between the buttons, `Home`/`End` to the ends, and the last-focused button is remembered. The toolbar sits left of the field, after the grip: the stacked ↑ ↓ pair with the × beside it, so the delete button moves from the far right of the row into the toolbar (one toolbar instead of two Tab stops per row, at the price of a slightly narrower field). It is drawn as a soft group: a tint of the ink colour at about 7% opacity, no border, a faint divider before the ×, muted icons that darken on hover, and the usual focus ring on the one button that has focus; a disabled arrow is dimmed. A row therefore costs two Tab stops, its field and its toolbar. `Alt+ArrowUp`/`Alt+ArrowDown` in the field move the row without leaving the field (the caret stays where it was) and use the same announcement as the buttons.
- **Reordering.** Arrows are real buttons: stacked ↑ ↓ (each 1.75 × 1.625rem, inside the 52px row height) in their own grid column between the grip and the field, always visible, `disabled` at the edges. After a move, focus stays on the same button of the moved row so repeated presses keep moving it. Drag uses Pointer Events on the grip only: `pointerdown` captures the pointer, the row follows with a transform, the other rows shift by row midpoint, `pointerup` commits, `Escape` or `pointercancel` restores; the grip has `touch-action: none` and is hidden under `@media (hover: none)`. No drag-and-drop library (the list is short and the behaviour small); native HTML5 drag is not used because it does not work on touch. A polite live region announces "Ingrediënt 'x' staat nu op plaats 2 van 7" after any move.
- **Usage line slot.** Under the field a `<p>` renders `usedIn(rowId)` when it returns step numbers ("Gebruikt in stap 1, 5"); this change passes a function returning nothing, `edit-recipe-chips` supplies the real one.
- **Saving.** The section posts `ingredients` as a hidden JSON input of `{ text }[]` (never the client's parse: the server parses the text itself with the same function, so what is stored cannot be forged or drift). `recipeValidation.ts` gains `readIngredients(form)` and a per-row error (`Vul bij "250 g" ook een naam in.`) returned as `errors.ingredients[index]`; the section shows it under that row and focus goes to the first failing row. Blank rows are dropped before validation.
- **Storage.** `updateRecipe` gets an optional `ingredients` argument; when given it deletes the recipe's ingredient rows and inserts the new ones with positions inside the same `db.batch` as the update, so the replace is atomic (a D1 batch is a transaction). When it is omitted nothing is touched (this keeps older callers and `recipe-editing › Recipe is updated` valid). The edit loader returns ingredients as lines; `createRecipe` already stores them. Deleting the old rows cascades to the unused `step_ingredients` rows, as `recipe-storage` specifies.

## Risks / Trade-offs

- A unit missing from the list lands in the name → harmless, easy to extend, and chips/scaling later show it.
- A mirror/input mismatch (fonts loading late, zoom, subpixel rounding) could misalign the colour by a pixel → both layers use the same CSS class and `font-display: swap` is already in use; checked at 100%, 200% zoom and on a phone during apply.
- Pointer-event dragging is bespoke code → kept small, the arrows are the primary accessible path and are always present.
- Replacing ingredient rows changes their database ids on every save → nothing references them by id today.
