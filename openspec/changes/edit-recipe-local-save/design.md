# Design

## Context

After the other five changes the editor has one client-side state object: the `Draft` of `edit-recipe-basics` extended with `photo` path (`image`), `ingredients` rows, and `steps` with `chips`, `ghosts` and their anchor ranges. Everything in it is plain JSON. Both routes render `RecipeEditor` with the starting values from their loaders; `isDirty` compares the state to the starting values; `edit-recipe-basics` guards leaving with `useBlocker` and `beforeunload`. The recipe page links to the edit route with a plain link. The identity (email) is available to routes through the root loader. See proposal.md for scope.

## Goals / Non-Goals

**Goals:**
- Never lose typed work to a reload or a closed tab; never show half-written recipes to anyone else.
- Predictable moments when a draft ends: save, reset, or the "Bewerk" link.

**Non-Goals:**
- Syncing drafts between devices, merging a draft with a recipe changed elsewhere, server-side drafts, offline editing or saving.
- Keeping an in-flight photo upload across a reload.

## Decisions

- **Storage and key.** `localStorage`, key `cookbook:draft:<email>:<slug|new>` (email lowercased, from the signed-in identity). The email in the key keeps two family members who share a browser profile from seeing each other's drafts; it never leaves the device. Chosen over IndexedDB because the payload is a few KB of JSON and the API is synchronous, which matters for flushing on `pagehide`, where async work may not finish. `sessionStorage` is not used because drafts must survive closing the tab.
- **Format.** `{ v: 1, savedAt: ISO string, base: { updatedAt?: string }, state: EditorState }`. `EditorState` is exactly what the editor holds, including chip modes, `ignored` proposals, ghosts and anchor ranges, so a restored editor is identical, not a re-derived approximation (anchors are not stored on the server, so only the draft can carry them across a reload). `v` bumps whenever the editor state's shape changes; a draft with another `v`, unparsable JSON or a missing field is ignored and removed.
- **A small module, `lib/draftStore.ts`, with an injected `Storage`** (`saveDraft`, `loadDraft`, `clearDraft`, `purgeDrafts`, `draftKey`), pure and unit-tested with an in-memory fake that can also throw (quota, disabled storage). Every call is wrapped so a failure returns `{ ok: false }` and never throws into the UI.
- **When to write.** A hook `useDraftPersistence(state, initial, key)`: debounce 400 ms after a change; flush immediately on `visibilitychange` to hidden, `pagehide` and when the editor unmounts. When `!isDirty(initial, state)` the draft is removed instead of written, which covers "changed back to the stored recipe" and "reset". A field that is still uploading (the photo) is replaced by the previous photo path in what gets written.
- **When to read.** On mount in a layout effect (before first paint after hydration, so a restored draft does not flash the stored values): read the draft; if present and valid, set the editor state to it and remember `restoredAt = savedAt` for the notice. The server-rendered HTML still shows the stored values, so with slow JavaScript the stored recipe is briefly visible; accepted.
- **Fresh start from "Bewerk".** The link on the recipe page passes `state={{ fresh: true }}`. The editor, on mount, checks `useLocation().state?.fresh`; when set it clears the draft, renders the stored values and immediately `navigate(location.pathname, { replace: true, state: null })`, consuming the flag. History state survives a reload, so without the replace a reload would start fresh again and eat the new draft; with it, a reload restores. Typing the address, using a bookmark, the back button into an old entry and reloads carry no flag and restore the draft. The header's "Nieuw recept" link carries no flag either, so an unfinished new recipe is picked up again. Chosen over a query parameter (visible, shareable, would persist) and over clearing in the recipe page (the recipe page should not know about editor drafts).
- **Ending a draft.** Save: both routes get a `clientAction` that calls the server action and, when its result is a redirect (success), clears the draft before returning it; a refused save (400) passes through and leaves the draft, and the editor's own effect re-writes it from the returned values if needed. How a redirect surfaces inside `clientAction` is verified in the first task; if it cannot be told apart reliably, fall back to writing a `saved:<key>` marker on submit that the next page load of any route consumes and clears with the draft, and that the editor deletes when a refused save comes back. Reset: the editor state becomes the starting values, which is not dirty, so the persistence hook removes the draft. Cancel: a plain link; the draft stays (it is just navigation; "Herstel" is the way to throw work away).
- **Narrowed guard.** `useBlocker` and `beforeunload` from `edit-recipe-basics` now depend on `dirty && !draftKept && !submitting`, where `draftKept` is the result of the last write (`ok`) and false when storage is unavailable or full. The bar text: "Niet opgeslagen · Concept bewaard op dit apparaat" while dirty and kept; "Niet opgeslagen" alone when the write failed; the restored notice reads "Concept van <tijd> hersteld" (relative: "vandaag 14:32", "gisteren 09:10", else the date), and disappears with the next change or when the bar is dismissed.
- **Server moved on.** The edit loader returns the recipe's `updated_at` (`getRecipe` selects it); a draft stores it as `base.updatedAt` when its first change is written. On restore, if the loader's `updatedAt` differs from `base.updatedAt`, a notice above the title says "Dit recept is intussen gewijzigd" with two buttons: "Concept houden" (updates `base.updatedAt` to the current value, so the notice does not return) and "Opnieuw beginnen" (clears the draft and shows the stored recipe). Neither is the default; nothing is replaced silently. Saving still overwrites (last write wins, as before). A new recipe has no base and never shows this notice.
- **Cleanup.** On editor mount, `purgeDrafts` removes keys with the `cookbook:draft:` prefix whose `savedAt` is more than 30 days old, then keeps only the 20 most recently saved, whoever they belong to (they are all this browser's). Unreadable entries under the prefix are removed too.
- **Storage failure.** If a write throws (quota, private mode, disabled), the editor keeps working, `draftKept` is false and the original leave confirmation returns; nothing else is shown, since an error banner for a convenience feature would be noise.

## Risks / Trade-offs

- A restored draft can contain chip anchors that no longer fit a changed ingredient list or text → anchors are validated on restore (ranges inside the body, rows still present) and invalid ones are dropped to unanchored pinned chips, reusing the logic that opens a stored recipe.
- History state is not reliable in every browser's back/forward cache → the worst case is a draft kept when a fresh start was expected, which "Herstel" resolves; the opposite (a draft lost) cannot happen because the flag is consumed only after the clear.
- Shared family computer with several browser profiles: handled per profile by the browser; the email in the key handles one profile used by several people.
- `v` bumps discard drafts across deploys that change the editor state → acceptable for a convenience cache; keep the editor state shape stable when possible.
- Drafts are kept even after "Annuleren", so someone may be surprised by a restored draft → the notice says what happened and "Herstel" removes it in two taps.
