# Design

## Context

`getRecipe` returns steps as plain strings, `createRecipe` stores them, nothing updates them. The editor shell and `Draft` come from `edit-recipe-basics`; `edit-recipe-ingredients` built the always-visible stacked arrows, the pointer-event drag on a grip and the move announcements for the ingredient rows. The mockup fixes the step: a header (grip, "STAP N", ↑ ↓, trash), a white bordered text box that grows, and later the chips under it. `edit-recipe-chips` needs two things from the text field that no plain `<textarea>` gives: marks under exact character ranges, and the exact range each edit replaced. This change provides both and nothing chip-specific.

## Goals / Non-Goals

**Goals:**
- Writing steps is typing and Enter.
- A `StepText` component whose mark layer and edit reports are exact and tested, so chips can be built on it without revisiting text handling.

**Non-Goals:**
- Chips, anchors and how marks map through edits (`edit-recipe-chips`); step photos; rich text; splitting a step at the cursor with Enter.

## Decisions

- **Draft shape.** `Draft.steps: { id: string; body: string }[]` (`id` is a client-only key, as for ingredients). The list always has at least one step; unlike ingredients there is no automatic empty trailing row, because Enter and "Stap toevoegen" are the ways to continue and an extra empty step per section would be noise. `edit-recipe-chips` adds `chips` to each step.
- **Enter semantics.** At the end of a non-blank step, Enter adds a step below and focuses it. Anywhere else Enter is swallowed, and so is Shift+Enter. A step is one paragraph (the recipe view renders it as one block), and splitting a step at the cursor would force chips and their anchors to be split too; that can be added later without changing stored data. Enter during IME composition (`isComposing`) is left alone, since it confirms the composition.
- **Pasted line breaks.** The browser's own paste happens (native undo keeps working); `onChange` then replaces each `\n` in the new value by a space. This is one-for-one, so the length is unchanged and the replaced-range maths stays exact. The server also replaces line breaks and trims.
- **Text layer (`StepText.tsx`).** The same stack as the ingredient rows but multi-line: a CSS grid with three children in one cell: a white `box`, a `mirror` `<div>` (aria-hidden, `pointer-events: none`, transparent text, `white-space: pre-wrap`, `overflow-wrap: anywhere`, identical border, padding, font and line-height to the field), and the real `<textarea>` (transparent background, `resize: none`, `overflow: hidden`). Because the mirror holds the same text, it sets the cell's height, so the field grows without JavaScript (and a trailing zero-width space keeps a final newline-free line measured). Marks are `<mark>` elements inside the mirror that only use `background` and `text-decoration` (underline with `text-underline-offset`, no border, padding or margin), so adding, changing or removing a mark never changes layout. Its input is `marks: { id, start, end, kind: 'auto' | 'manual', hot?: boolean }[]` in UTF-16 indexes of `value`; overlapping marks are not supported (the first wins), chips never produce them. Chosen over `contenteditable`, which would own undo, IME and mobile keyboard quirks that the textarea gets right natively.
- **Edit reporting (`lib/textEdit.ts`, pure).** `computeEdit(prev, next, hint?) → { start, removed, inserted }` meaning: the characters `[start, start + removed)` of `prev` were replaced by `inserted` characters of `next`. The browser layer supplies a hint in `beforeinput`: the selection `[selectionStart, selectionEnd)` before the change; on `input`, the replaced range is the hinted selection and `inserted = next.length − (prev.length − (end − start))`. That is exact for typing, paste over a selection, cut, delete and drop (the browser reports a selection range for those). When there is no usable hint, or the hint is inconsistent with the lengths (undo and redo, autofill, spellcheck replacement), `computeEdit` falls back to the longest common prefix and suffix of `prev` and `next`, which is exact whenever the change is one contiguous replacement (always true for these events); when the replaced text equals its replacement in an ambiguous place (deleting one of three equal letters), either position is a valid answer. Every result is snapped outward to whole code points (never between the two halves of a surrogate pair, so emoji and astral characters are never split). Chosen over reading `InputEvent.getTargetRanges()` (not available for textarea) and over a plain always-diff approach (ambiguous for repeated characters when a hint exists).
- **IME.** `compositionstart` records the text before; no edits are reported during composition (the controlled value still updates so the field shows the candidate text); `compositionend` reports one edit by diff against the recorded text. Reporting happens through `onEdit(edit, nextValue)` on the component, called in the same event as `onChange`, so a consumer updates its ranges and the value together.
- **Reordering.** The arrow pair, the drag hook and the announcement live region are extracted from the ingredient list to `shared/recipeEditor/` as a second user now exists (STRUCTURE.md: move when a second route or component needs it); the steps use the same behaviour with the arrows in the header, left of the trash button. The step's text, and later its chips, move with its `id`.
- **Keyboard.** The header's ↑, ↓ and trash buttons form one `role="toolbar"` (`aria-label` "Acties voor stap N") with a roving tabindex: one Tab stop, `ArrowLeft`/`ArrowRight`/`Home`/`End` inside it; the toolbar comes before the text in the DOM, so a step costs two Tab stops. It is drawn like the ingredient toolbar: a soft group (ink tint at about 7%, no border, a faint divider before the trash, muted icons that darken on hover), right-aligned in the header, always visible. `Alt+ArrowUp`/`Alt+ArrowDown` in the text move the step with focus and caret kept; the plain arrows keep moving the caret, and Tab is never remapped (see the ingredients design for why assistive technology is not detected). Enter-at-the-end remains the fast way to continue.
- **Undoable delete.** Deleting a non-blank step replaces it in the list by a slim placeholder row ("Stap verwijderd · Ongedaan maken") that restores the step on use and removes itself after 8 seconds (or when another edit happens); deleting a blank step is immediate. The placeholder is not part of the draft and never posted.
- **Saving.** The section posts `steps` as a hidden JSON input of `{ body }[]`. The server trims each body, turns line breaks into spaces, drops blank ones and stores positions in order. `updateRecipe` extends its optional arguments with `steps`: when given, it deletes the recipe's step rows and inserts the new ones inside the same `db.batch` as the update (atomic); when omitted, steps are untouched. `edit-recipe-chips` extends this insert with the chip columns.

## Risks / Trade-offs

- Replacing step rows on every save drops `steps.image`/`image_alt` → nothing writes them today; if step photos arrive, saving must carry them through instead of replacing.
- The textarea/mirror pair must stay pixel-identical: any CSS that touches one must touch the other → both use one shared class, and the apply tasks check wrapping at several widths, 200% zoom and with long unbroken words.
- The `beforeinput` hint differs between browsers for some input types (autofill, dictation) → that is exactly what the prefix/suffix fallback covers, and both paths have unit tests.
- Swallowing Enter in the middle of a step may surprise someone expecting a line break → accepted for now; the proposal records it as a deliberate choice.
