# Design

## Context

New recipes are made in `RecipeEditor`, which keeps a draft (`draft.ts`, kept on the device by `useDraftPersistence`) and starts it with `startingDraft(rules, seed)`. A seed holds the fields as strings, the ingredient lines as plain text and the steps as `Step` objects; `startingDraft` ties stored chips to their words, and the editor proposes chips, quantities and timers for plain text. `PhotoField` shrinks a chosen file (`resizePhoto`), uploads it (`uploadPhoto`, POST `/foto`) and holds the resulting `/foto/<uuid>` path; it does this when the file is chosen, not on save. See proposal.md for motivation.

The Worker runs on Cloudflare (D1, R2). Every request is checked in `handler.ts`. A browser script cannot read another site's response (CORS), so a page or image from a recipe site must be fetched by the Worker.

`harden-requests` (in flight) adds a Content-Security-Policy and refuses data-changing requests from another origin. `record-recipe-source` (must land first) adds the `source` field to the form, the draft and `DraftSeed`.

## Goals / Non-Goals

**Goals:**
- A pasted address prefills the new recipe form, including the photo, with as little code of our own as the sites' own data allows.
- A fetch endpoint that cannot be turned into a way to reach private systems or to burn resources.

**Non-Goals:**
- Site-specific scrapers (we read only the schema.org data and never add or maintain site code), importing tags, import in the edit form, cleaning up photos of discarded forms.

## Decisions

- **Hand-written JSON-LD reader behind one seam.** `recipe-scrapers-ts` was checked and rejected: it only knows 27 named sites, has no generic schema.org mode and flattens `HowToSection` steps badly. The rest of the code talks only to `readRecipe(html, url)` in `lib/import/readRecipe.ts`, which returns `{ title, intro, servingsText, minutes, ingredients: string[], steps: string[], image }` or undefined. It parses the HTML with the browser's `DOMParser`, reads every `script[type="application/ld+json"]` (a bad block is skipped), finds the first node whose `@type` is or contains `Recipe` (top level, in an array, or in `@graph`), and maps it: `name`, `description`, `recipeYield` (string, number or array: the first entry), `totalTime` (else prep + cook) as an ISO 8601 duration to minutes, `recipeIngredient` (strings), `recipeInstructions` (a string split on line breaks and numbering, a list of strings or `HowToStep`, or `HowToSection`s whose `itemListElement` steps are flattened), and `image` (string, array, or `ImageObject` with `url`, resolved against the page address). HTML tags and entities are stripped from every text.
- **Parse in the browser, proxy on the Worker.** The Worker only fetches; the reader needs a DOM parser, so it runs only in the browser. The existing recognition code runs in the browser anyway, so the imported text goes straight into it.
- **Two POST endpoints, JSON body `{ url }`**, outside the layout like `/foto`: `POST /importeren/pagina` answers the HTML, `POST /importeren/foto` answers the image bytes. POST so the same-origin rule of `harden-requests` covers them, the address does not end up in logs or caches, and no link can trigger a fetch. Errors are statuses without body: 400 bad request or address, 403 refused address, 413 too large, 415 wrong content type, 429 rate limited, 502 site unreachable or error, 504 timeout. Names follow `STRUCTURE.md`: `ImportPageFetchRoute.ts`, `ImportImageFetchRoute.ts`, in `routes/import-fetch/`, with the guard in `lib/safeFetch.server.ts`.
- **`safeFetch(url, { maxBytes, accept, fetch })` is the one place with the rules.** It parses the address with `new URL`, allows only `http:` and `https:`, refuses credentials, refuses `localhost`, names ending in `.local` or `.internal`, and literal IPs in loopback, private, link-local, unique-local, carrier-grade NAT, multicast and reserved ranges (IPv4, IPv6 and IPv4-mapped IPv6; the URL parser normalises odd notations such as `0x7f.1` and `2130706433`, so the check runs on the parsed host). It follows redirects by hand (`redirect: 'manual'`), at most 5 hops, checking every hop's address with the same rule; sends a plain `User-Agent` and `Accept`; aborts after 10 s; checks the `Content-Type` against the allowed kind; and reads the body as a stream, stopping at the size cap whatever `Content-Length` says (5 MB page, 2 MB image, the same cap as uploaded photos). The `fetch` is a parameter so tests need no network.
- **Image: the bytes, nothing more.** The proxy checks the content type and size only; `storePhoto` still decides by magic bytes when the browser uploads it, so a mislabelled response is refused there as before. The proxy is a public-ish fetcher, so it also serves images only to signed-in family members like everything else.
- **Rate limit with the Workers Rate Limiting binding**, 30 per 60 s, keyed by the member's email, one count per request to either endpoint. The binding sits behind a tiny `allow(key)` in the env context so tests inject a fake. Task 1 also confirms the binding works with the local dev setup (Miniflare); if it does not, tests use the fake and a manual check covers dev.
- **The ceiling of the address check is stated, not hidden.** A hostname that resolves to a private address cannot be seen before the fetch (a Worker has no DNS lookup of its own). It is accepted because a Worker's `fetch` runs on Cloudflare's edge and cannot reach a private network; the name rules above are defence in depth, noted with a `ponytail:` comment on the guard. If the app ever fetches from inside a network, this needs a resolver check.
- **Menu:** `site-menu` is modified with the full requirement text, based on the version in the in-flight `tag-manager` change (which adds "Tags"), so this change lands after it. The link "Recept importeren" sits right below "Nieuw recept" for every role.
- **Entry point: its own page `/recepten/importeren`**, not a box on the plain new recipe form, so the new recipe form stays as it is. `ImportRecipePageRoute` renders the same `RecipeEditor` with a `canImport` prop that only it sets, and shares the loader and action of `NewRecipePageRoute` (one place in `edit-recipe/` that both routes re-export), so a save is the same save. There is no navigation to carry a prefill: `RecipeEditor` renders `ImportBox` while the draft equals the starting values (`!dirty`). Both pages share the one draft a new recipe has on the device. Importing sets the draft with `importedDraft(rules, importedSeed)` (like `startingDraft`, but the steps are plain text and get the chips a typed step would get; `startingDraft` treats steps as stored ones and ghosts the words that say something) and hands the fetched image to `PhotoField`. Because the form is then dirty, the box disappears and the draft persistence keeps the import like any edit; Herstel (reset) returns to the starting values and the box with it. A failed import changes nothing, so the box stays and can be tried again. This avoids a confirm dialog for overwriting typed work.
- **Mapping to the seed** is one pure function, `toDraftSeed(imported, url, base)`: title and intro as text; servings the first whole number of the yield text (empty if none or below 1); time written the way the rest of the app writes time (the format is checked against `RecipeView` and the seed data in the task); ingredient lines as given; steps as `{ body, ingredients: [] }` so the editor's recognition proposes the chips; `source` is the address; author and tags come from `base` (the starting seed, so the author stays the calling name); image is not in the seed but returned next to it. Text is trimmed, line breaks inside a line become spaces, empty entries are dropped, and a field over the size limits of `limit-field-sizes` (if merged first) is cut by the editor's existing limits, not by the importer.
- **`PhotoField` gets an `incoming` prop**: a `Blob` plus a counter so the same image can be handed twice. An effect passes it through the same path as a chosen file (the body of `choose` after reading the file moves into `take(blob)`), so shrink, preview, upload, replace, remove and error messages are shared. Unreadable input shows the existing "cannot be read" message.
- **Image failure is separate from page failure.** The image is fetched after the form is prefilled: first `readRecipe`, apply the draft, then fetch the image and hand it over. A failure there shows "De foto is overgeslagen." in the import box area and nothing else changes. The box is gone by then (form is dirty), so the message lives in the editor next to the photo field, cleared by the next photo action.
- **Under `harden-requests`**: the proxies are same-origin POSTs and need no CSP change; the preview of the imported photo is a `blob:` URL and `/foto/...` after upload, both already allowed there. A task checks it by hand once both changes are in.
- **Dutch UI texts** (box label, button, messages) are written in the task, not the spec; the spec asserts that a message exists.

## Risks / Trade-offs

- [Sites that block bots or need JavaScript give "page could not be fetched" or "no recipe found"] → Accepted; there is no headless browser here, and the message tells the user to type it in.
- [Some sites' schema data is messy: steps as one string, `HowToSection` groups, ingredients with HTML] → `readRecipe` flattens sections, splits a single string on blank lines/numbering, and strips tags; whatever is still odd shows in the form, which is the review step anyway.
- [The proxy fetches arbitrary sites for any family member] → Family-only, the guard, caps and the rate limit; the limits are in the spec so they are tested.
- [An imported photo stays in R2 if the form is discarded] → Same as an abandoned chosen photo today; the separate orphaned-photos change handles it.
- [Copyright of imported text] → Content stays in the family's private cookbook and the source address is recorded.
- [`record-recipe-source` not merged yet] → This change is applied after it; the `source` field is part of `DraftSeed` by then.
