# Design

## Context

The recipe page (`routes/recipe/route.tsx`) has a two-column grid from 52rem and one column below it. `StepList` shows one expanded "current" step with Vorige/Volgende; `IngredientList` is a checklist. Steps reach the page as `string[]` from `getRecipe`. The visual world is established (Mulish, 3px ink borders, hard shadows, red/jade/blue tokens in `app.css`, seals); this change inherits it and adds no identity, token or dependency unless one turns out to be missing.

Per-step chips are not stored yet. A later change adds the tables, the edit form and the loader; this one builds the UI against the data shape that change will deliver.

A clickable HTML preview of the agreed design exists as a private Artifact (https://claude.ai/artifact/BRSSn67NUWEnHYppdRSPbg, Appeltaart with 13 steps). Where this document and the preview differ, this document wins; the preview deliberately skips the points listed under "Not in the preview".

## Goals / Non-Goals

**Goals:**
- A page that works while cooking: scroll only, big targets, nothing hidden behind gestures.
- A chip data shape the UI can render now and the later storage change can fill without UI changes.

**Non-Goals:**
- Storing chips, editing them, suggesting them (see Deferred), step photos, scaling servings, saving "done" marks or timers beyond the browser tab.

## Decisions

- **Step shape.** The page works on `Recipe` from `lib/recipes.ts`, which uses `StoredRecipe`'s field names (`id`, `slug`, `title`, `author`, `time`, `servings`, `intro`, `image`, `seal`, `ingredients: { quantity_text, name }[]`) and whose `steps` are `Step[]`: `Step = { body: string; ingredients: { quantity_text: string; name: string }[]; ovenTemperature?: number; timer?: { minutes: number; label?: string } }`. A step has at most one oven temperature and one timer, and a timer renders and behaves differently from the other chips. Chips hold no ingredient id: a chip is free text, so "kruid bij met zout" needs no salt row. Making `StoredRecipe` equal to `Recipe` (tables, edit form, loader) is a later change; it only has to fill what the page already reads.
- **Hardcoded recipes for now, a way to see the design.** Chips cannot be stored yet, so the recipe route's loader reads `findRecipe` from `lib/recipes.ts` (the sample recipes, with the Appeltaart of the preview holding every kind of chip) instead of D1; `getRecipe` stays in `.server/recipes.ts` with its own tests and returns when `StoredRecipe` equals `Recipe`. Tests never use the sample recipes: each builds its own steps and recipes.
- **Layout switch with container-free CSS.** Below 52rem: tabs. From 52rem: two columns. One markup, switched by CSS (`max-[52rem]:` / `min-[52rem]:` variants), never a `matchMedia` read during render, to avoid a hydration flash. Effects that need to know the layout (dock, cook mode) read a `matchMedia('(min-width: 52rem)')` listener after mount. (The preview uses container queries only so its "Telefoon" switch works on a desktop screen; the real page uses viewport queries.)
- **Tabs.** A `<div role="tablist">` bar plus two panels, both always rendered; CSS shows only the active panel below 52rem. The bar is `position: sticky; top: env(safe-area-inset-top)` with a `z-index` above content. Real `role="tab"` buttons with `aria-selected`, `aria-controls`, arrow-key navigation and roving `tabindex`. Active tab: the red of the header with white text and the hard shadow; each at least 40px tall in a bar of about 56px, in the page's paper colour with a 3px ink rule below.
- **Panels fill the screen (narrow).** Each panel gets `min-height: calc(100svh - <tab bar height>)`, so that scrolled to the bottom only the tab bar, the timer row and the panel's content are on screen, and a short ingredient list sits at the top of its panel rather than at the bottom of a short page. The first implementation of this in the preview is approximate (a fixed offset); the real one should measure the sticky stack (tab bar plus dock when present) so the sum is exactly the screen height, and should be checked on a phone with the browser's collapsing address bar (`svh` versus `dvh`).
- **Remembered scroll.** A scroll listener keeps `window.scrollY` in a per-tab ref while the sticky stack is stuck (`getBoundingClientRect().top <= 0.5`); scrolling back up leaves the last value in place. On a tab change the tab being left is noted, and a layout effect applies `arrive(positions, from, to, headingTop, stackHeight)`: the new tab's position if it has one; else, if the old tab has one, the new tab's heading offset by the sticky stack (the uppermost stuck position); else no scroll at all. Positions are plain component state, not persisted; switching uses `behavior: 'instant'`. An earlier version saved the position at the moment of leaving and always scrolled on a first visit, which jumped the page when switching from the top and lost the position after a stray scroll up.
- **Sticky stack.** Tab bar then, when needed, the timer dock directly under it, as one sticky container so the dock cannot drift from the bar. The dock sits over the content (no space reserved), only exists while it has a timer. `scroll-margin-top` for steps and headings equals the stack height so "go to step" never ends under it.
- **Steps.** `<ol>` of `<li>`s, the same design at every width. Each step: a head line with a small uppercase red "Stap N" label (0.8125rem, 900, tracked) followed by the chips, then the text as one `<button aria-pressed>`. Tapping dims the step as done: the text at 45% and the ingredient and oven chips at 60% opacity, never struck through; the square in the label turns jade with a check. Steps are separated by a dashed rule at 28% ink, no numbers in boxes and no connecting line (they cost too much width on a phone). Step text is `clamp(1.25rem, ..., 1.5rem)` at weight 800.
- **Done square.** The label starts with a 14px square that is always present: empty with a muted 2px border, or filled jade with a white check when done. Same size in both states so nothing shifts. It is a visual echo of `aria-pressed`, not a control of its own (the whole step text is the target).
- **Chips.** A chip is small (0.875rem), muted text on a faint ink tint (8%) with a small radius and no border: they help so you do not have to switch to the ingredient list, and must not outweigh the step text. Quantity in blue and oven degrees in red. Ingredient and oven chips are `<li>`s; oven has a small thermometer icon. Timers are different on purpose: a filled jade button with a hard shadow and a play icon, at least 40px tall.
- **Chip wrapping.** The head line is `display: flex; flex-wrap: wrap` with two children: the label and the chip group (`display: flex; flex-wrap: wrap; flex: 1 1 auto`, Tailwind `flex-auto`, not `flex-1`, whose basis of 0 would keep the group beside the label and squeeze it). A flex item's base size is its max-content width, so when the whole group does not fit beside the label the group wraps as one to the next line, and only there wraps internally. `align-items: center` on the group so a chip does not stretch to the height of a timer button. A step without chips has no group. List markers are off on the group's items.
- **Timer state.** One `useTimers(recipeSlug, steps)` hook at the page level (so the dock, sidebar and steps share it), holding for each timer `{ endsAt, remainingMs, state: 'idle' | 'running' | 'finished' | 'native' }`. State is derived from absolute `endsAt` timestamps, not decremented ticks, so background tabs and reloads stay correct; a single `setInterval(250ms)` runs only while a timer runs. Timer id is the index of its step (a step has one timer). `endsAt` persists to `sessionStorage` under a key containing the slug and is read after hydration (never during render). The pure part (`start`, `add`, `stop`, `restore`, ordering) is a module with unit tests that take `now` as an argument.
- **Timer at the step.** Narrow: a running or finished timer becomes a full-width card in its own line below the step's head (so the other chips do not move): the countdown at about 2.25rem in jade, the label, and buttons +1, +5, "App" with an alarm icon (when available) and stop with a stop icon; finished shows "Stap N klaar" in white on red with +1, +5 and "Klaar". Wide: the timer chip stays chip-sized and only replaces the duration with the countdown ("Klaar" in red when finished); it is not a button while running, because all controls are in the sidebar.
- **Timers stay in view.**
  - *Narrow:* a dock row (about 44px, yellow with ink rules) directly under the tab bar, on both tabs, holding running and finished timers whose step is less than half in view below the tab bar, so a step half covered by the tabs already docks its timer (one `IntersectionObserver` with a top margin equal to the tab bar and several thresholds; a step taller than the visible area counts as in view when it fills half of it). A pill is `step-number badge · countdown · label`; finished pills are red and pulse (not colour alone: the text says "Klaar"). The row scrolls sideways when the pills do not fit; with the expectation of at most about two timers at once, there is no overflow design beyond that.
  - *Wide:* a "Timers" block on top of the sticky ingredient column, listing all running and finished timers regardless of the scroll position (an earlier version hid timers whose step was in view, and the constant coming and going while scrolling was annoying). Each card shows badge, countdown, label, +1, +5, a right-arrow button to go to the step (accessible name and tooltip "Ga naar stap N") and stop (or Klaar when finished).
  - *Order:* by step index, then by position within the step, not by start time, so that pills do not appear out of nowhere in the middle of the scroll and the order is the one the recipe has.
  - *Animation:* only a pill/card that is newly shown animates in (a short scale/fade, none under reduced motion). The animation must be tied to the element's first appearance (a stable key per timer, the element not re-created when siblings change), so starting or extending a timer never replays it on the others; the preview re-creates the whole list and so does replay it.
- **Sidebar scroll (wide).** The sticky column is `display: flex; flex-direction: column; max-height: calc(100svh - 2rem)`: the timer block and the heading do not shrink, the ingredient list takes the remaining height and scrolls by itself (`overflow-y: auto`, `overscroll-behavior: contain`). Accepted trade-off: the more timers are shown, the shorter the visible part of the list.
- **Go to step.** The jump control in the dock pill, and the arrow in the sidebar card, scroll the step into view (with the stack offset, smooth unless reduced motion) and highlight it for about 3 seconds: a yellow tint over the step between its dashed rules (the same box as the sidebar hover, so the two look alike) that fades in and then out (in by 20% of the time, held until 60%, out by the end), starting immediately together with the scroll, also when the step is already in view (a delay would only disrupt). With `prefers-reduced-motion` the tint is shown steady for the same time and then removed. A repeated jump restarts the highlight.
- **Finish signal.** On the tick that crosses zero: set state `finished`; play a short beep with the Web Audio API (one `AudioContext` created in the click handler that starts the timer, because browsers require a user gesture); `navigator.vibrate?.([200, 100, 200])`; set `document.title` to `⏰ Stap N · <title>` and restore the original when no timer is finished. Cards, pills and sidebar cards switch to the red state with the words "Stap N klaar" and a pulse that stops under reduced motion.
- **Clock app (per timer, Android only).** The page cannot ask the phone for a timer through any web API. On Android Chrome an `intent:` link with action `android.intent.action.SET_TIMER` can start the clock app's timer, with `android.intent.extra.alarm.LENGTH` (seconds), `android.intent.extra.alarm.MESSAGE` (the label) and `android.intent.extra.alarm.SKIP_UI`; it must come from a user tap and the browser may ask first. There is no public equivalent for iPhone (only a Shortcuts link to a shortcut the person installs themselves, not offered). The page cannot learn when the phone's timer ends or cancel it. Therefore: a *choice per timer*: a running timer has an "App" button (with an alarm icon) that hands over the time that is left, for long waits where the page is probably closed when the timer ends (a short timer while working stays in the page); and a *setting*, off by default and kept in `localStorage` (a per-device convenience that must work with it missing), that hands every timer over as soon as it is started. A handed-over timer becomes a dashed note "In je app · 14:32" with its label below and two buttons: "Herstel" takes the timer back and it runs here as if it had never been handed over (the end time is kept while handed over, so it continues from the original start, or shows as finished when it has ended since), and "Wis" removes the note and ends the timer (it cannot cancel the phone's timer, and says so in its accessible name). Control and setting are shown only when the device is Android (user-agent client hints or `navigator.userAgent`, behind one function), nowhere else. Where the setting lives in the interface is open (a small link under the cook switch is the candidate). A web push notification sent by a Worker at the end time would also work with the screen off, but needs an installed web app and server work; it is not in this change.
- **Cook mode.** A `useWakeLock` hook wraps `navigator.wakeLock.request('screen')`, exposing `state: 'unsupported' | 'off' | 'on' | 'refused'`; it re-requests on `visibilitychange` when wanted and releases on unmount. A separate `useCookMode` decides *wanted*: `manual: boolean | undefined` (undefined means automatic). Automatic wants it when the first item of the open tab (first ingredient, or first step on Bereiding) has its top above the middle of the viewport, or any ingredient is ticked; the same rule on both tabs, evaluated on scroll and on tab change, so changing tabs does not turn it off. Using the switch sets `manual` and ends automatic behaviour. Both are component state, so a reload or another recipe (the route component remounts with a new `key`) starts automatic again. The switch is a `role="switch"` button, full width, placed directly above the tab bar (so it can be seen turning on while scrolling to the tabs, and is not part of the sticky stack), narrow screens only, with text "Scherm blijft aan" / "Scherm mag slapen" / "Scherm kan niet wakker blijven" reflecting the actual state, not the wish, and a second line ("Gaat vanzelf aan zodra je begint", "Automatisch, tik om uit te zetten", "Handmatig", "Je browser staat dit niet toe"). The knob's position inside the switch is still to be tuned.
- **Ticked ingredients lift.** A ticked ingredient is marked by its filled jade circle and dimmed to 55% opacity, not struck through. Ticking state moves up from `IngredientList` to the page (it already lives in a `Set`), because cook mode reads it. Tabs keep both panels mounted, so nothing is lost on switching.
- **Hover, focus and press (to implement; the preview does not have them).** Only where a real pointer exists (`@media (hover: hover)`), so touch screens never get a stuck hover.
  - *Timer chip (idle):* hover lifts it by 1px and grows the hard shadow from 3px to 4px with a slightly lighter jade; press moves it down 2px and shrinks the shadow (as `Button` does today); cursor pointer; the play icon nudges 1px right.
  - *Timer card and sidebar card buttons (+1, +5, jump, stop, App, Klaar):* hover fills the button with the yellow token and keeps the ink border; stop turns red on hover; the "Klaar" button (ink) goes to jade; press translates 1–2px; all keep a visible `:focus-visible` ring (the existing 4px blue outline).
  - *Dock pills:* hover raises the border to ink-on-yellow and shows an arrow glyph after the label to hint that it navigates; press scales to 0.97; cursor pointer.
  - *Running chip on a wide screen (not a button):* no hover state, to avoid looking operable; its title attribute names the timer.
  - *Sidebar card:* hover on the card itself highlights its step lightly (the same tint as the jump highlight, without the fade) so you can see which step it belongs to without clicking. The tint is also cleared when the card disappears under the mouse (stop, done), by the card's own cleanup, because an unmounted element gets no mouseleave.
  - *Step text:* hover tints the row with white at 70% (already in the preview).
  - *Reduced motion:* the lifts and nudges become instant colour changes.
- **Tests at the lowest level.** Pure logic (timer reducer, restore from storage, ordering of timers, cook-mode decision, scroll-memory bookkeeping, clock-app availability) gets unit tests with injected `now`/stubs. Behaviour that needs layout, intersection or a real wake lock gets a named `test.todo` with the reason on the line above, and is checked by hand in `pnpm dev` at 360px, 768px and desktop width.

## Not in the preview

Hover and focus states, the "only a new timer animates" rule and ordering by step (the preview orders by start and replays the animation), measuring the tab/dock height for the panel minimum, `localStorage` for the clock-app setting, persisting timers over a reload, real intent links (the preview only shows the resulting note), and the position of the cook switch's knob.

## Deferred

- **"Suggest chips" while editing a recipe.** When storage and the form arrive, a button proposes chips from the step text; the author accepts, edits or drops them. The first version is procedural (regular expressions for "30 minuten", "180 °C", "200 g bloem"), and its limits will show on real recipes: a step saying "gebruik de overige bloem" after "200 g" of a 300 g ingredient needs bookkeeping across steps that a pattern match cannot do. Option kept open, not decided: Cloudflare Workers AI with a small model that only extracts quantities and intent ("uses 200 g bloem", "uses the rest of bloem"), with ordinary code doing the arithmetic (300 − 200 = 100 g rest), always shown as suggestions. It needs no client download, but it sends recipe text to Cloudflare, so it needs a conscious yes given that the cookbook is private by default. An in-browser model was rejected for now: hundreds of MB, WebGPU and weak Dutch.
- **Storing chips** (three tables), **step photos** (thumbnail beside the step text opening in a `<dialog>`) and **scaling servings** (chips could carry optional amount and unit then) are separate changes.
- **Push notification when a timer ends** (see Clock app).

## Risks / Trade-offs

- Chips are not stored yet, so the recipe pages show hardcoded sample recipes and cannot show real ones until the next change → accepted, it is how the UI gets reviewed first.
- Wake Lock needs a secure context and, in some browsers, a user gesture; automatic start can be refused → the switch says so honestly instead of claiming success.
- Sound and vibration are limited by the browser and the device's silent mode; the visual and title signals back them up, and cook mode keeps the screen on while timers run.
- The wide sidebar list shrinks with each timer shown, down to a few rows with many timers → accepted, the list scrolls.
- Restoring scroll across a differing page height (fonts loading) can be off by a few pixels → accepted.
- `sessionStorage` timers are per browser tab: a second tab starts with none. Fine for a kitchen phone.
- A handed-over timer cannot be cancelled or observed from the page → the note says what was handed over and nothing more.
